# Как сделать следующий ролик

Всё, что нужно, лежит в этой папке — заново скачивать и настраивать ничего не
надо. Ниже: что где, что менять, как собрать быстро и на какие грабли не
наступать (все уже наступили один раз, чтобы вы не наступали второй).

## Два пайплайна — какой выбрать

| | `build_captions.sh` | `build.sh` |
| --- | --- | --- |
| Когда | у вас есть **точный текст** озвучки | текста нет, только аудио |
| Синхронизация | субтитры «слово за слово», привязаны к реальным паузам в дорожке | раскадровка растягивается пропорционально длине аудио |
| Вход | `voice.mp3` + `script.txt` (одна фраза — одна строка) | `voice.mp3` |
| Экран/сцены | `render/index2.html`, `render/scenes2_a.js`, `render/scenes2_b.js`, `render/main2.js`, `render/captions.js` | `render/index.html`, `render/scenes_a.js`, `render/scenes_b.js`, `render/main.js` |

**Всегда предпочитайте `build_captions.sh`**, если текст есть — точность
попадания в слово несравнимо выше, а стоит это той же цены по времени.

## Быстрый старт

```bash
cd video
./build_captions.sh assets/voice_wb_leaks_profit.mp3 assets/script_wb_leaks_profit.txt build/out.mp4
# или без точного текста:
./build.sh assets/voice_wb_unit_economy.mp3 build/out.mp4 --target 54.2
```

Оба скрипта сами: поднимают шрифты (`fetch_fonts.py` → `render/fonts.css`,
один раз), линкуют Playwright, **линтят** сцены (`lint_scenes.mjs` — падает
до рендера, если видит один из старых багов, см. ниже), считают тайминги,
рендерят **параллельно** (`capture_parallel.mjs`) и **проверяют** результат
(`verify_render.py` — длительность, наличие видео/аудио потоков, yuv420p).
Всё в `build/` — временное.

## Скорость: почему рендер параллельный

`capture_parallel.mjs` делит кадры на N кусков (по умолчанию N =
`nproc/2`, здесь `2`) и рендерит их **одновременно** в N отдельных вкладках
Chromium, каждая — свой процесс ОС (Playwright не шарит процесс рендерера
между страницами), плюс каждая пишет в свой ffmpeg. В конце куски
склеиваются без перекодирования (`-c copy`) и один раз домешивается звук.

Замер на этом ролике (49.55 с, 60 fps, 2973 кадра, 4 ядра):

| | время | кадров/с |
| --- | --- | --- |
| `capture.mjs` (один поток) | 6.4 мин | ~7.7 |
| `capture_parallel.mjs` (2 воркера) | ~3.3 мин | ~15 |

`--workers` можно поднять, но помните: КАЖДЫЙ воркер — это Chromium-страница
**и** свой ffmpeg, оба грузят CPU. На 4 ядрах `workers=2` — разумный баланс;
`workers=4` может не дать выигрыша (или проиграть) из-за конкуренции за
ядра между 4 страницами и 4 кодировщиками одновременно — если поднимаете
`--workers`, перепроверьте время на реальном ролике, не считайте на глаз.

`capture.mjs` (однопоточный) остаётся для `--stills` (быстрые PNG-стопкадры)
и `--start/--limit` (кусок для отладки) — там параллелить нечего, накладные
расходы на N браузеров того не стоят.

## Что менять под новый сценарий (пайплайн с субтитрами)

| Задача | Где править |
| --- | --- |
| Текст, порядок реплик | `assets/<script>.txt` — одна фраза на строку, пустые строки не нужны (но не мешают) |
| Какая сцена на какую реплику | `BEATS` в `render/main2.js` — каждый beat ссылается на индексы карточек `CAPTIONS.cards[from..to]` |
| Сама сцена (фон, графика) | `render/scenes2_a.js`, `render/scenes2_b.js` |
| Типы склеек | поле `tr` в `BEATS` (`soft`/`whipL`/`whipR`/`whipU`/`zoomIn`) |
| Стиль субтитров (шрифт, подсветка слова, положение) | `render/captions.js` → `captionBar()` |
| Цифры юнит-экономики (агрегат) | `GATES`, `COGS`, `PROFIT`, `REVENUE` в `render/scenes_a.js` |
| Цифры юнит-экономики (на 1 продажу) | `UNIT_PRICE`, `UNIT_SEGS` в `render/scenes2_b.js` |

Индексы карточек — по счётчику строк в `assets/<script>.txt`, начиная с 0.
Проверить разбивку: `python3 analyze_captions.py voice.mp3 script.txt` без
`-o` печатает список `[start - end] текст` — по нему считаются индексы для
`BEATS`.

Beat = функция `(ctx, p, lt, gt, A)`, как и раньше (`p` — прогресс окна
0..1, `lt` — секунды с начала beat'а, `gt` — глобальное время, по нему через
`CAPTIONS.cards[N]` можно достать точные тайминги слов конкретной фразы —
так сделаны «ворота» расходов в `beatGates()`, где каждое слово открывает
свои ворота секунда в секунду).

## Проверять глазами до полного рендера

```bash
node capture.mjs --entry index2.html --config build/captions.json --stills "2.5,24,42"
node lint_scenes.mjs render/scenes2_a.js render/scenes2_b.js   # без рендера вообще
node profile.mjs                                               # стоимость примитивов в мс/кадр
```

Один кадр рисуется ~25–40 мс. Если сцена в `profile.mjs` даёт сотни мс —
ищите живой `blur`, а не «тяжёлую графику» (см. грабли ниже).

## Грабли — уже наступили, чтобы вы не наступали

Каждая теперь либо чинится автоматикой (лint/дефолт), либо задокументирована.

1. **`ctx.filter = 'blur(...)'` на каждом глифе** — Chromium заводит слой
   размером с холст на КАЖДЫЙ символ: сцена финала стоила 658 мс/кадр вместо
   25. Расфокус в `kinetic()` теперь делается тремя смещёнными копиями
   глифа, а не canvas-фильтром.

2. **`kinetic(..., { p: clamp(x * K) })`** — кинетический текст сам плавно
   раскрывает буквы по мере роста `p` мимо 1.0 (нужен запас: длинная строка
   требует `p` заметно больше 1, иначе последние буквы застревают
   недо-раскрытыми на месте — именно так один раз залипла строка
   «ТОВАР ПРОДАЁТСЯ ОТЛИЧНО…»). **Не оборачивайте `p` в `clamp()` перед
   передачей** — `kinetic()` уже клэмпит прогресс на уровне каждой буквы.
   `lint_scenes.mjs` теперь ловит этот паттерн автоматически и валит сборку.

3. **`chip()` с длинным текстом уезжает за край кадра.** Теперь `chip()`
   сама читает текущую трансформацию canvas (`ctx.getTransform()`) и, если
   вызывающий код не передал `maxW`, вычисляет безопасную ширину до
   ближайшего края кадра — переполнение больше не должно происходить само
   по себе. Для `text()`/`kinetic()` такой автоматики нет (они часто рисуют
   заголовки специально НАРОЧНО на грани кадра ради композиции), поэтому
   `lint_scenes.mjs` вместо этого требует явный `maxW` у любого вызова
   `text()`/`kinetic()`, где строка приходит из переменной, а не написана
   в коде буквально — на такое проще один раз явно решить, сколько места
   можно занять, чем гадать.

4. **Живой blur у подложек** — только через `plate()`: блюр считается один
   раз и кешируется как спрайт.

5. **`shadowBlur` большого радиуса на больших фигурах** — спрайты
   (`glow()`, `dot()`, `streakSprite()`), кешируются по цвету.

6. **`measureText` в цикле** — `fitSize()`/`layout()` кешируют метрики.

7. **Кодек**: `-preset slow` на 1080×1920@60 — ~1 кадр/с на 4 ядрах,
   становится узким местом. `veryfast --crf 18-19` — ~8 кадр/с на одном
   потоке, ~15 кадр/с на двух параллельных.

## Синхронизация с голосом

`analyze_captions.py` **не использует ASR** (Whisper недоступен из песочницы
— egress-политика блокирует HuggingFace, openaipublic, download.pytorch.org).
Вместо этого: `ffmpeg silencedetect` даёт реальные паузы в дорожке, текст
режется на карточки по строкам, слова получают вес = длина символов, и вся
эта раскладка растягивается на «время речи» (паузы вычитаются), а потом
конвертируется обратно в реальное время через границы найденных пауз. Это не
настоящий forced alignment, но на спокойной начитке с короткими фразами
(как в этом ролике) даёт попадание в слово с точностью до ~0.1–0.2 с — тому,
кто смотрит, разницы с честным ASR не видно.

Если Whisper всё же станет доступен (другая песочница, другая политика) —
`transcribe.py` уже написан (`faster-whisper`, `word_timestamps=True`),
осталось только подключить его вывод вместо пропорциональной раскладки в
`analyze_captions.py`.

## Доставка

- Вложение в чат — не больше **30 МиБ**: делайте превью
  (`hqdn3d=1.5:1.5:6:6,fps=30`, битрейт подберите под длину так, чтобы влезть
  в лимит — например `-b:v 1900k` для ролика ~100 с).
- Для соцсетей — `-crf 23 -maxrate 12M` при 60 fps (~8-9 Мбит/с).
- Мастер (`crf 17-18`, ~25 Мбит/с) в репозиторий не кладём: GitHub режет
  файлы больше 100 МБ, а история распухает навсегда.

## Что уже лежит в репозитории

- `assets/*.mp3` — озвучки уже собранных роликов (можно пересобрать тот же
  результат кадр в кадр);
- `assets/*.txt` — тексты сценариев для пайплайна с субтитрами;
- `fonts/*.woff2` — сабсеты Montserrat и Inter, рендер работает офлайн;
- весь код рендерера, обоих сборочных скриптов, линт и проверка результата.

Готовые видеофайлы в репозиторий не попадают (см. «Доставка» выше) — они
жили в контейнере сессии; если нужно сохранить конкретный ролик надолго,
попросите закоммитить именно его или заберите присланный в чат файл.

## TODO для следующего ролика: звуковые эффекты

Пользователь попросил добавлять SFX поверх озвучки (тики, свуши на
склейках, удары на появлении цифр) — сейчас в аудиодорожке только голос
из ElevenLabs, домешанный ffmpeg'ом на последнем шаге, никакого SFX-слоя
нет. План на следующий раз:

1. **Синтезировать звуки процедурно**, а не брать сэмплы из сторонних
   библиотек — не тратим время на лицензии, легко подогнать длительность/
   тон под конкретный кадр, результат детерминирован (как и вся картинка).
   Проще всего через `ffmpeg`'овские генераторы (`sine`, `anoisesrc`,
   `aevalsrc`) с огибающей громкости через `afade`/`volume` — не нужен
   отдельный аудио-движок, достаточно короткого Python/bash-скрипта,
   который печёт нужные `.wav` один раз и кладёт в `assets/sfx/`.
2. **Timing уже посчитан** — `analyze_captions.py` отдаёт точные тайминги
   слов (`build/captions.json`), `analyze_audio.py` — тайминги склеек
   сцен (`build/audio.json`/`build/audio3.json` и т.п.). SFX накладывать
   на эти же метки: свуш на каждый `tr` в `BEATS`/`BASE`, тик — на срабатывание
   гейта в `beatGates()`/`scene4`, глухой удар — на появление крупного числа.
3. **Микс** — отдельным шагом `ffmpeg` после рендера видео: несколько
   `-i sfx.wav` с `adelay=<мс>` на каждый, свести через `amix`, наложить
   поверх голоса (`-filter_complex "[voice][sfx_mixed]amix=inputs=2:weights=1 0.35"`),
   и только этот сведённый трек передавать в `capture_parallel.mjs --audio`.
   Не трогаем видео-пайплайн вообще — звук готовится заранее, как отдельный
   файл, ровно так же, как сейчас туда передаётся голос.
